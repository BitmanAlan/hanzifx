# ADR-001 渲染路径：自己写 Playwright 逐帧截图 + 系统 ffmpeg

- 状态：已采纳（2026-11-19 评审通过，按这条做原型；原型的验收报告见 `reports/P0-验收.md`）
- 作者：渲染底座维护者
- 范围：`engine/`（渲染底座）和 `styles/001-variety-outline/`（第一个风格）

## 结论

1. **风格是纯函数**：`create(root, ctx)` 只按参数和画面尺寸搭好 DOM/SVG，`seek(t)` 把这一刻所有会动的属性从头算一遍写进去。结果只取决于 t，不看上一帧、不看真实时钟、不用 `Math.random()`。风格代码零依赖，只用浏览器原生的 HTML/SVG/CSS/JS。
2. **同一份风格代码三种用法**：试玩页（`engine/player/`）里实时播放、拖时间轴、改参数；导出页（`engine/render/`）里被逐帧截图，再用 ffmpeg 编成 MP4（竖屏、横屏）或者透明底（ProRes 4444 `.mov`、VP9 `.webm`、PNG 序列）。两个页面加载的是同一个 `src/host.js` 和同一个 `style.js`。
3. **渲染器选自己写的 Playwright 逐帧截图**，不用 HyperFrames 当底座，不用 Remotion，不依赖 GSAP。理由见下面的比较。因为风格不绑定渲染器，以后给 HyperFrames 或 Remotion 写一层适配器都只是薄薄一层。

## 三条路的比较（许可证都看了原文）

| | HyperFrames | 自己写 Playwright 逐帧截图 | Remotion |
|---|---|---|---|
| 许可证 | Apache-2.0（看的是 2026-06-04 的版本，上游提交 8228932e） | 我们自己的代码；依赖 playwright-core 是 Apache-2.0 | **Remotion License**（`LICENSE.md`，提交 c86fc72，2026-11-09）：个人、3 人以内的营利公司、非营利组织、试用评估可以免费用；**其他公司要买 Company License**；不许拷它的代码做自己的衍生品来卖。文件开头还写了 5.0 版许可证会改（PR #3750） |
| 动画依赖 | 播放器依赖 `gsap ^3.12.5`，核心里有 GSAP 时间轴解析器，默认写法是 GSAP 时间轴 | 不依赖任何动画库，缓动和弹簧自己写成解析式纯函数（`src/lib/ease.js`） | React 组件 + `useCurrentFrame()` |

| 透明底 | 支持（ProRes 4444 / VP9 / PNG 序列） | 支持，自己接 ffmpeg | 支持 |
| 确定性 | 本地模式截图；Docker 模式用 BeginFrame，跨平台一致 | 本机逐帧一致（已验收）；跨机器没测 | 本机一致，有官方 Lambda 分布式渲染 |
| 扩展接口 | Frame Adapter，文档写明 **v0 实验版，可能有破坏性改动** | 我们自己定，`ctx` 和返回值见 `docs/写一个新风格.md` | 稳定 |
| 用户装起来 | `npx hyperframes`，连带 GSAP 和它的编译器 | `npm i` 三个依赖 + 系统里的 ffmpeg + 一个浏览器 | `npm i` 一堆 React 依赖，公司用户先买许可 |

### 为什么不用 Remotion

库的用户只要是在 4 人以上的公司里用（MCN、品牌方、代运营，正好是我们的目标用户），就得先给 Remotion 买 Company License。这是开源库用户的门槛，不能当默认路线。已经有 Remotion 许可的用户，以后可以用适配器把我们的风格嵌进 Remotion 工程（风格是纯函数，适配器就是在 `useCurrentFrame()` 里调 `seek(frame / fps)`）。

### 为什么不依赖 GSAP

GSAP 3.15.1 的 `package.json` 里写的许可证是「Standard 'no charge' license: https://gsap.com/standard-license」，不是 OSI 认可的开源许可证。原文（Webflow 的 GSAP Software License Agreement）里：

- 禁止用途（Prohibited Uses）：用在「让用户不写代码就能做可视化动画、并且跟 Webflow 的可视化动画功能竞争」的工具里，要事先拿到书面同意。
- 终止：Webflow 发现不合规时可以「按自己判断」终止许可，终止后要停用并销毁所有副本。
- 修改：Webflow 可以随时改条款，继续用新版本就算接受。
- 常见问题里也写了：带可视化界面做动画的工具如果拿不准算不算禁止用途，请联系他们。

我们的交互画廊（拖时间轴、改字、改色、导出）正好踩在这条边上。所以底座和风格都不用 GSAP，弹跳、弹簧、缓动、抖动全部自己写（`src/lib/ease.js`、`src/motions/index.js`），共一百多行。

### 为什么不用 HyperFrames 当底座

它本身是 Apache-2.0，没问题；问题在它带进来的东西：播放器依赖 GSAP（上面那条风险）；编译器默认去拉 Google 字体（中文要专门绕）；扩展接口还是 v0 实验版。我们要的功能（逐帧截图、透明底、ffmpeg 编码）自己写不到 1000 行，换来依赖少、字体全自己控制、接口自己定。以后要用它的 Docker 确定性渲染或 Lambda，可以写一个 Frame Adapter 接进去。

## 浏览器从哪来和自检

- 顺序：`--chrome` 或环境变量 `HANZIFX_CHROME` 指定的 → 已经下载的 chrome-headless-shell → 本机装的 Google Chrome。
- 跟最初设想的「优先用已经装好的 Chrome」有一点不同，这里先说清楚：**用户不用另外下载**这一条做到了，本机有 Chrome 就能导出；但如果 headless-shell 已经在，我优先用它，因为它的版本跟 playwright-core 一起锁死，逐帧结果最稳；本机 Chrome 会自动升级，升级后逐帧 hash 可能变。要反过来（本机 Chrome 优先），改 `cli/lib/browser.mjs` 里两段的顺序就行（评审后定的是现在这个顺序，见文末第 2 条）。
- 只用逐帧截图，不用录屏：新版无头 Chrome 录屏会裁掉画面边缘，也不认 deviceScaleFactor（评审时提出的坑）。视口和 DSF 写死为画面尺寸和 1，每帧截图后核对 PNG 尺寸，编码后用 ffprobe 再核一遍，不对就报错。
- `npm run doctor`：逐项检查 Node、Intl.Segmenter、ffmpeg、ffprobe、三个编码器、浏览器、字体，缺什么就给一行补救命令。

## 渲染流程（`cli/lib/pipeline.mjs`）

1. 解析参数：默认值 → 预设（配色 C*、节奏 R*）→ 用户覆盖（`src/lib/params.js`，浏览器和 Node 共用）。
2. 分词（准备阶段，见下面「分词」），结果作为输入数据传给风格。
3. 字体：按字体链给每个字找字体，主字体没有的落到备用字体（出警告），整条链都没有就报错退出；按实际用字做子集。
4. 开浏览器，视口 = 画面尺寸，DSF = 1；挂载风格；用开发者协议 `CSS.getPlatformFontsForNode` 查每个文字节点实际用的字体，出现字体链以外的字体就报错。
5. 逐帧：`seek(i / fps)` → 截图 → 写 `frames/000001.png`，记 sha256。可以开多路并行、打乱顺序（帧号决定文件名，跟渲染顺序无关）。
6. 透明底时逐帧解 PNG，查 alpha 和描边有没有碰到画面边缘；竖屏再查安全区。
7. ffmpeg 编码，ffprobe 核尺寸和像素格式。
8. 写 `manifest.json`（输入、环境、字体、逐帧 hash、输出 hash、全部检查结果）和 `timeline.json`（表演数据）。

截图两条路（实测出来的坑）：

- 不透明底：直接走开发者协议的 `Page.captureScreenshot`，开 `optimizeForSpeed`。渐变背景的 PNG 压缩是瓶颈，这样从每帧约 300 毫秒降到约 67 毫秒；101 帧竖屏两路并行从 29.5 秒降到约 6 秒。
- 透明底：走 Playwright 的 `omitBackground`。**开发者协议直接截图在整帧全透明时会丢掉 alpha 通道**，存成不透明的 RGB（第一帧还没出字时就是这样，进成片就是一帧黑）。Playwright 这条路空帧也保留 alpha。两条路都核 PNG 的颜色类型，透明底不是 RGBA 就报错。

## 确定性的范围（写清楚边界）

- 已验收（条件：同一台机器、同一个浏览器版本、底座默认的启动参数，见 `cli/lib/browser.mjs` 的 `CHROME_ARGS`）：同一个 ffmpeg，导出两次：截图逐帧 sha256 一致、MP4 解码后逐帧 md5 一致、MP4 文件逐字节一致；4 路并行加打乱顺序，跟顺序渲染逐帧一致（这条同时证明风格是纯函数）；透明底两次（第二次乱序）逐帧一致。
- 没验证：换一台机器、换操作系统、换浏览器版本以后是不是逐帧一致。字体都是我们自己下发的网页字体，不受系统字体影响，但栅格化可能因平台不同有差异。要跨机器一致，下一步是 Docker 里固定浏览器（可以借 HyperFrames 的做法）。
- x264 默认是确定性的（只有加 `--non-deterministic` 才不是），但线程数跟 CPU 核数有关，换机器文件字节可能不同，解码后的画面差异要另测。

## 逐帧一致的几类坑（2026-11-20 对照实验）

背景：几个风格各自碰到过「乱序渲染偶发对不上」，各自绕开（隐藏、取整、不倾斜），以后每写一个风格都要重踩一遍，所以拿修复前的版本在底座层面找统一办法。

**决定**：浏览器启动参数默认加 `--disable-partial-raster`（关掉局部重新栅格化）。它修好了两类，渲染慢约 6%（透明底 18.2 秒 → 19.4 秒，演播室底没区别）。另外两类它修不好，照旧写成硬规矩（见 `docs/写一个新风格.md` 第 3 节）。

**对照数据**（`npm run determinism`，每个例子 5 轮，每轮 4 路乱序＋1 路顺序；「对不上」＝跟第一轮比有帧的 sha256 不同的渲染次数）：

| 例子 | 复现用的版本 | 尺寸和底色 | 开着局部重画 | 关掉局部重画（现在的默认） | 结论 |
|---|---|---|---|---|---|
| 缩成一个点（006 V3 竖排按钮入场） | 开发版本 | 9:16 透明底 | 1 次 | 0 次 | 修好，规矩降成建议 |
| 整组亚像素平移（005 V3 镜头平移，开发时留的复现版本） | 开发版本 | 16:9 透明底 | 9 次 | 0 次 | 修好，规矩降成建议 |
| 整组淡出（002 出场整组 opacity，在开发版本上加一行复现） | 开发版本＋1 行 | 9:16、16:9 × 演播室、透明 | 14 次 | 15 次 | 修不好，照旧是硬规矩 |
| 倾斜加模糊（004 V3） | 开发版本 | 9:16、16:9 × 演播室、透明；另照开发时的命令（透明底 mov，4 路乱序对 1 路顺序）各 3 轮 | 0 次 | 0 次 | 开发时复现过，现在复现不出来，照旧是硬规矩 |
| 文字非等比缩放（003 印章字横向拉宽 1.35 倍＋V3 推近，开发中发现） | 本地版本 | 9:16 演播室 | 5 次（6 次里） | 5 次 | 修不好，新增硬规矩 |
| 小字跟着整组每帧换缩放（003 印章字约 40 像素＋V3 推近，横屏） | 本地版本 | 16:9 演播室 | — | 3 次（4 次里） | 印章改成只挪位置、不跟着缩放，就一致了；写进第 8 条的同类情况 |
| 几乎没动的一帧（008 V1 出场第一帧：整张卡只往下挪 0.007 像素，差在头像外圈左边一小条，115 个像素、不透明度最多差 7） | 开发版本 | 16:9 透明底 | — | 5 次（8 次里） | 修不好：两种画法随机出现，跟乱序还是顺序无关，两种都不等于上一帧；`--num-raster-threads=1` 8 次里 6 次、`--disable-gpu` 3 次，也都修不好。风格层绕开：动的量不到 1% 就当没动（进场尾巴、出场开头各留一小段死区），改完一致。写成建议，见 `docs/写一个新风格.md` 第 3 节 |
| 几乎没动的一帧，后面整段停住的画面都跟着变（012 判对 V1：勾画完后的震动在第 36、37 帧只挪 0.02–0.04、0.0002 像素，字的位置跟着入场弹簧在第 29–36 帧只挪 0.001–0.02 像素；之后的停留段第 39 帧起 37 帧，勾的右上那一头约 110×93 像素、92 个像素最多差 8 个色阶） | 开发版本 | 16:9 透明底 | — | 2 次（6 次里，平面单独跑） | 开 `HANZIFX_RESET_FRAME=1`（每帧先回 0 再截）8 次全一致，说明是前面几帧带进来的状态；先怀疑过「勾画到头时虚线长度正好等于路径长度」，去掉虚线以后照样对不上，不是这个原因。风格层绕开：震动位移、字的位置尾巴不到 0.05 像素就当没动，判对、判错 × 平面、糖果各 8 轮（16 次渲染）全部一致 |

「复现用的版本」指开发时的提交；公开仓库只带最终版本，不含开发历史，表里的结论按当时的复现记录写。

**「几乎没动的一帧」比看上去严重**：012 那一例里，出问题的不是那一两帧本身，而是它们后面整整一段停住的画面——前面某一帧只挪了零点零几像素，后面每一帧（画面完全没变）都跟着随机出两种画法。所以衰减到静止的动作（震动、弹簧、衰减冲击）一律要在尾巴设死区，最后一点点直接落到正好的静止值，别让它慢慢爬过去。底座的 `shake`、`bounceIn` 也要加（排在所有互动元素换完以后，紧接着全库逐帧一致再跑一遍）。

**试过、没用的参数**（拿整组淡出那个例子试，9:16 演播室底，3 轮 6 次渲染，每种都还是对不上 3 次）：`--disable-gpu-rasterization`、`--disable-gpu-compositing`、`--disable-gpu`、`--num-raster-threads=1`。单线程光栅化对「缩成一个点」那个例子也没用，所以不是多线程分块的先后顺序。

**复位帧**（「每帧截图前强制整页重绘」的一种做法）：每截一帧之前先 seek 到 0 秒、截一个 1×1 的小图逼浏览器真画一帧，让每一帧的「上一帧」都一样。整组淡出的例子用它就 0 次对不上，但这个例子耗时 21 秒 → 38 秒，003 的例子 126 → 158 秒（慢 25%–80%）；文字非等比缩放用它照样对不上（像是字形缓存，影响不止一帧）。整组透明度已经有硬规矩、各风格都绕开了，不值得让所有导出都慢这么多，所以只留成排查开关 `HANZIFX_RESET_FRAME=1`，用了会记进 `manifest.json` 的 `env.resetFrame`。

**排查工具**：`HANZIFX_EXTRA_ARGS="--a --b"` 临时加启动参数（记进 `env.extraChromeArgs`）。用了这两个开关的导出，不在逐帧一致的保证范围里。

## 分词（PLAN.md 第 5 条，分三层）

| 层 | 是什么 | 在哪算 |
|---|---|---|
| 第一层 | 作者用 `|` 标的切分，比如「这也太\|好笑了吧」 | 解析时直接用，显示时去掉 `|`（要显示竖线用全角「｜」） |
| 第二层 | jieba-wasm + 本项目补充词表（`src/lib/lexicon.js`，加词频 200000） | 导出：Node 端准备阶段；试玩台：用户第一次改字时才在浏览器里加载 |
| 第三层 | 浏览器自带 Intl.Segmenter + 补充词表 | 兜底（试玩台 jieba 还没加载完时） |

jieba-wasm 的评估：

- 许可证：jieba-wasm（fengkx）MIT；它把 jieba-rs（messense）当子模块编进去，MIT；jieba-rs 内嵌的词典 `jieba/src/data/dict.txt`（5,071,843 字节）来自 jieba 原项目（Sun Junyi，MIT），跟原项目的 `jieba/dict.txt` 大小只差 9 字节。代码和词典都核了。
- 体积：一份 wasm 4,015,140 字节（词典打在里面），gzip 后 2,805,808 字节。包里有 node、web、deno、bundler 四份，npm 解包共 16 MB。
- 速度：Node 里首次加载约 7 毫秒，短句每句约 5 微秒（2000 句 10 毫秒）。
- 一致性：Node 和浏览器用的是同一个包的同一份 wasm 和词典，补充词表也一样。验收里 10 句两端切词完全一致。
- 效果（实测，不是留出集评测）：ICU 切错的「这/也/太好/笑了/吧」「绝/绝/子」「误/区」「人工/智能」jieba 都对；「家/人们」「笑/死」「冲/鸭」jieba 也错，靠补充词表修正。
- 没选的：@node-rs/jieba（MIT，原生模块只能在 Node 用，浏览器还得另一套，两边结果可能不一致）；nodejieba（MIT，C++ 原生模块要编译，装起来麻烦）。

检查分两种：

- 卡发布：「词中间断行」用跟排版**同一套**分词和词表来查（独立重新切一遍、按原文位置比对，不信排版函数自己的结论）。
- 只提示：再用 Intl.Segmenter 独立切一遍，断行位置在 ICU 眼里也在词中间的，出提示（比如「也太｜好笑」），用来补词表。

要老实说明的一点：补充词表现在的 100 多个词是我凭经验写的，写的时候还没有开发集；留出集我没打开过。开发集到了以后，我按开发集重新整理词表，并在版本记录里写清楚哪些词是开发集之前就有的。

## 字体（详见 `FONTS.md`）

- 只用 OFL：站酷快乐体（主）、站酷庆科黄油体（备选主字体）、思源黑体 Noto Sans SC（备用字体，可变字体固定成 wght 900）。来源地址钉在 google/fonts 的具体提交上，下载后校验 sha256。
- 子集：导出时按这次实际用到的字做；试玩台用 GB2312 全部 6763 个汉字加常用标点的常用字子集；备用字体在试玩台走本地服务按需做子集。
- 字体链：每个风格在 `meta.fontFallback` 里声明。检查 `missing-glyph` 区分两种：「完全缺字」（整条链都没有，报错退出）和「用了备用字体」（警告，风格会变味）。实测：快乐体缺「喆堃垚」，导出时这三个字落到思源黑体上；「😂」整条链都没有，直接报错。
- 一个坑：思源黑体是可变字体，固定字重以后 name 表不跟着改，浏览器报的字体名是「Noto Sans SC Thin」（以前记忆里也记过），字形实际是 900。所以核对字体时按我们实际下发的子集文件自己的 name 表来认，不按名字猜。
- 竖排（005 要用）：子集默认保留全部排版特性和替换字形。实测思源黑体子集里 vert、vrt2 都在，「「，（」都有竖排替换字形；破折号「—」在这款字体里没有竖排替换，005 要另外处理（转 90 度或换字形）。竖排要用 HTML 的 `writing-mode: vertical-rl`，让浏览器自己套 vert 特性，不能只把字转 90 度。

## 不选的方案（Rejected）

- **Remotion 当默认渲染器**：公司用户要买许可证（见上）。
- **HyperFrames 当底座**：带进 GSAP 和会拉 Google 字体的编译器；扩展接口是实验版。留作以后的适配器。
- **GSAP**：非开源许可，禁止用途跟交互画廊重叠，许可方可以单方面终止和修改条款。
- **录屏（Playwright recordVideo、CDP screencast）**：会裁边、不认 DSF，时间也不精确。只用逐帧截图。
- **浏览器里直接导出（WebCodecs）**：SVG/DOM 画面没法稳定地画进 canvas（字体和 foreignObject 都有坑），只有纯 canvas 的风格能用。以后画廊的「直接导出」可能对一部分风格用它，但不当主路线。
- **风格一律用 canvas 画**：会丢掉 CSS 的中文排版能力（竖排 `writing-mode`、`vert` 特性、`text-spacing-trim`）。契约允许风格自己选 SVG、HTML 或 canvas。
- **npm 打包 ffmpeg（ffmpeg-static）**：等于我们在分发 GPL 二进制，让用户自己装更干净。
- **Python fontTools 做子集**：要多装一个 Python 运行时。Node 里用 harfbuzz（subset-font）就够了；fontTools 只在我做核对时用，不进依赖。
- **只用 Intl.Segmenter 分词**：口语切错太多（实测过）。
